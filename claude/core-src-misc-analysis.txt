2. ISSUES FOUND & FIXES APPLIED
================================================================================

--- Issue 1: greasedLineTools.ts (Line 162) - LOOP CONDITION BUG ---
Severity: HIGH
Type: Logic Error

The MeshesToLines method has a for loop with two index variables:
  for (let i = 0, ii = 0; i < indices.length; i++)
Inside the loop body, `ii` is incremented 3 times (once per triangle vertex).
The condition `i < indices.length` causes the loop to run `indices.length`
times, but there are only `indices.length / 3` triangles. This means `ii`
exceeds the array bounds after the first third of iterations, causing
`indices[ii++]` to return `undefined` and producing NaN vertex positions.

Fix: Changed loop condition from `i < indices.length` to `ii < indices.length`.

--- Issue 2: stringDictionary.ts (Line 47) - FALSY VALUE BUG ---
Severity: HIGH
Type: Logic Error

The `getOrAddWithFactory` method checks `if (val)` before adding a factory-
produced value to the dictionary. This prevents valid falsy values (0, false,
empty string, null) from being stored. The class docs explicitly state values
can be "anything including 'null' but except 'undefined'".

Fix: Changed `if (val)` to `if (val !== undefined)`.

--- Issue 3: codeStringParsingTools.ts (Line 94) - LOOSE EQUALITY ---
Severity: LOW
Type: Type Safety

The `IsIdentifierChar` function uses `v == 95` (loose equality) while all
surrounding comparisons use strict operators (`>=`, `<=`). Since `v` is
always a number from `charCodeAt(0)`, this works in practice, but using `===`
is safer and consistent with the rest of the comparisons.

Fix: Changed `v == 95` to `v === 95`.

--- Issue 4: textureTools.ts (Line 237) - LOOSE EQUALITY ---
Severity: LOW
Type: Type Safety

The `FromHalfFloat` function uses `e == 0x1f` (loose equality) while the
preceding check on line 235 uses `e === 0`. Since `e` is always a number
(from bitwise operations), this works, but strict equality is more consistent.

Fix: Changed `e == 0x1f` to `e === 0x1f`.

--- Issue 5: observable.extensions.ts (Line 89) - UNNECESSARY ITERATION ---
Severity: MEDIUM
Type: Optimization

In `notifyObserversWithPromise`, when `state.skipNextObservers` is true, the
code uses `continue` to skip to the next observer. Since `skipNextObservers`
remains true, this causes the loop to iterate through ALL remaining observers
doing nothing useful. Using `break` exits immediately.

Fix: Changed `continue` to `break`.

--- Issue 6: performanceMonitor.ts (Line 62) - DIVISION BY ZERO ---
Severity: MEDIUM
Type: Consistency / Correctness

The `averageFPS` getter divides by `this._rollingFrameTime.average` without
checking for zero, while `instantaneousFPS` (line 68-76) already has this
guard. When no samples have been added, `average` is 0 and `1000.0 / 0`
returns `Infinity`.

Fix: Added zero check consistent with `instantaneousFPS`.

--- Issue 7: sceneRecorder.ts (Line 155) - LOOSE EQUALITY ---
Severity: LOW
Type: Type Safety

In `_compareObjects`, the string type check uses `==` instead of `===`:
  Object.prototype.toString.call(originalValue) == "[object String]"

Fix: Changed `==` to `===`.

4. NOTES ON DISMISSED REPORTS
================================================================================

Several potential issues were reported during analysis but dismissed after
manual verification:

- andOrNotEvaluator.ts recursive call (line 30): The recursion is bounded
  because _HandleParenthesisContent always simplifies the query string
  (replaces expressions with "true"/"false"), so eventually it terminates.

- smartArray.ts push bounds (line 46-50): The code writes to
  `this.data[this.length++]` then checks if length > data.length. JavaScript
  arrays grow dynamically, so `this.data[this.length++] = value` is valid
  even when length equals data.length. The subsequent capacity doubling is
  an optimization hint, not a correctness issue.

- tags.ts RemoveTagsFrom (line 134): `for (const t in tags)` on an array
  iterates indices as strings ("0", "1"), and `tags[t]` correctly accesses
  values. While not idiomatic (should use `for...of`), it works correctly.

- observable.ts notifyObserver scope (line 473): This is a deliberate design
  choice. `notifyObserver` targets a specific observer directly, unlike
  `notifyObservers` which iterates all observers. The scope is already set
  on the observer object and applied when needed.

- domManagement.ts textContent null (line 37): When nodeType is 3 (text
  node), textContent is never null per the DOM spec. The null case only
  applies to other node types.

- sceneRecorder.ts parameter name typo `originalObjet` (line 142): This is
  a private method parameter. While a typo, renaming it would be a cosmetic
  change with no functional impact, so it's not worth the code churn in a
  large open source project.
