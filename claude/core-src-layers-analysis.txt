================================================================================
ARCHITECTURE OVERVIEW
================================================================================

The Layers module follows a "thin" pattern where each layer has a "thin" version
(ThinEffectLayer, ThinGlowLayer, ThinHighlightLayer, ThinSelectionOutlineLayer)
that contains the core logic, and a "full" version (EffectLayer, GlowLayer,
HighlightLayer, SelectionOutlineLayer) that wraps the thin version and adds
scene-level integration, render targets, and post-processing.

Hierarchy:
  - Layer (standalone full-screen 2D layer for backgrounds/overlays)
  - ThinEffectLayer -> EffectLayer (abstract base for post-process effects)
    - ThinGlowLayer -> GlowLayer (emissive glow effects)
    - ThinHighlightLayer -> HighlightLayer (per-mesh highlight with stencil)
    - ThinSelectionOutlineLayer -> SelectionOutlineLayer (outline effect)

Scene components:
  - LayerSceneComponent: manages Layer instances
  - EffectLayerSceneComponent: manages EffectLayer instances

ISSUES FOUND & FIXES APPLIED
================================================================================

1. BUG: layer.ts - Unsafe splice with unchecked indexOf
   -------------------------------------------------------
   File: layer.ts, line 386-387
   Severity: Bug (potential data corruption)

   The dispose() method calls `this._scene.layers.indexOf(this)` and passes the
   result directly to `splice()` without checking for -1. If the layer is not
   found in the array (e.g., already removed), `splice(-1, 1)` removes the LAST
   element from the array, corrupting the layers list and potentially disposing
   the wrong layer.

   Fix: Added a guard to only splice when index !== -1.

2. BUG: thinEffectLayer.ts - Variable shadowing in transparent submesh loop
   -------------------------------------------------------
   File: thinEffectLayer.ts, line 508-509
   Severity: Code quality (variable shadowing)

   Inside the transparent submesh rendering loop, a new `const engine` is
   declared that shadows the outer `engine` variable. While both currently
   reference the same engine (through different paths), this shadowing is
   confusing and could lead to bugs if the code paths diverge in the future.

   Fix: Removed the inner variable declaration and reused the outer `engine`.

3. OPTIMIZATION: thinEffectLayer.ts - Redundant boolean logic
   -------------------------------------------------------
   File: thinEffectLayer.ts, line 741
   Severity: Code quality / readability

   The expression `this._dontCheckIfReady || (!this._dontCheckIfReady && this.isLayerReady())`
   is logically equivalent to `this._dontCheckIfReady || this.isLayerReady()`.
   The negation check is redundant because if _dontCheckIfReady is true, the
   short-circuit already prevents evaluation of the right side.

   Fix: Simplified to `this._dontCheckIfReady || this.isLayerReady()`.

4. OPTIMIZATION: thinSelectionOutlineLayer.ts - Same redundant boolean logic
   -------------------------------------------------------
   File: thinSelectionOutlineLayer.ts, line 334
   Severity: Code quality / readability

   Same issue as #3 above.

   Fix: Simplified to `this._dontCheckIfReady || this.isLayerReady()`.

5. CODE QUALITY: glowLayer.ts & highlightLayer.ts - map() used for side effects
   -------------------------------------------------------
   Files: glowLayer.ts line 334, highlightLayer.ts line 415
   Severity: Code quality

   `.map()` is used purely for side effects (setting `autoClear = false` on each
   post process). `.map()` creates and discards a new array, which is wasteful.
   `.forEach()` is the idiomatic choice for iteration with side effects.

   Fix: Changed `.map()` to `.forEach()`.

6. BUG: thinEffectLayer.ts - Floating promise for additional shader imports
   -------------------------------------------------------
   File: thinEffectLayer.ts, line 755-756
   Severity: Bug (race condition)

   `_additionalImportShadersAsync?.()` returns a Promise but is not awaited.
   The eslint-disable comment suppresses the warning, but this means additional
   shader imports may not complete before the shader is used, potentially causing
   rendering failures on first use.

   Fix: Added `await` to properly wait for the additional shader imports.

NOTES ON CODE NOT CHANGED
================================================================================

- The "thin" layer pattern (delegation via bound methods in EffectLayer
  constructor) is verbose but is a deliberate architectural choice for
  backward compatibility.

- Several `as any` casts in material property access (e.g., `(material as any).emissiveTexture`)
  are necessary because the base Material type doesn't expose these properties;
  they exist on specific material subclasses. This is an existing pattern
  throughout the codebase.

- The stencil reference auto-increment in ThinHighlightLayer
  (`ThinHighlightLayer.GlowingMeshStencilReference++`) is intentional for
  ensuring unique stencil references per instance.

- Array literal usage (e.g., `vertices.push(1, 1)` vs `const vertices = [1, 1, ...]`)
  is a consistent pattern across the codebase and not changed.
